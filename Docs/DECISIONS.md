# 决策与约定

已定下来的取舍、改 UI 的流程，以及踩过的坑。**改动前先看这里**，这些决定都有过一次"改了又改回来"的经历。

## 界面决策（已定，改之前先确认）

- **视觉方向是「精致数据面板」**（2026-10-16 选定）：中性画布 + 白色面板 + 1px 细边框，不用毛玻璃、渐变、阴影；层级靠字号。曾比较过「原生 macOS 质感」与「保留玻璃风格精修」，均未采用。
- **菜单栏下拉例外，用系统原生玻璃**（2026-10-18）：它属于菜单栏这层系统界面，和 Wi-Fi、控制中心的面板并排出现，所以不画自己的背景，让系统的液态玻璃透出来，布局也照原生面板：灰色小节标题、圆形图标徽章、内缩分隔线、底部菜单式行。主窗口仍是数据面板风格。
- **用量主环的颜色跟着超额预测走**：预测「紧张」变琥珀、「会超额」变红，而不只看已用百分比。原因：28% 的蓝环配一条「18 天后用尽」的红色提示，自相矛盾。
- **客户端页的进度条按风险着色（绿 / 琥珀 / 红），总览的「用量最高」条是单一品牌蓝**。两页不一致是有意为之：总览用来概览，客户端页是要定位问题的列表，扫一眼找出红/橙行更重要。2026-09-29 确认保持。
- **总览中间两栏等宽等高**，等高靠「图表随行高伸展」实现，不是把卡片拉高——拉高会在卡内留下空白，试过并被否掉。
- **客户端行不放首字头像，状态列放在名字前面**：头像不带信息（两人都显示「杜」），还把名字整体右推。状态（圆点 + 文字）放在第一列，宽窗口下不必从名字横跨整个窗口去找在线/离线；不用单独的圆点，那样状态只靠颜色表达。排名数字会随排序乱跳，不采用。
- **应用图标是「用量环」**（2026-10-18 选定）：品牌蓝底 + 白色 250° 圆弧，和应用里的用量环同一个形象，16px 也认得出。比较过车轮仪表、B + 进度环、服务器机架。侧栏标志 `BrandMark` 用同样比例绘制。
- **客户端排序靠点表头**：「客户端 / 上次在线 / 用量 / 配额」可点，再点一次切换方向；去掉了右上角的排序菜单。
- **超额预测画成细线时间轴**（2026-10-18 选定）：2px 细线，三个圆点标今天、预计用尽、重置，用尽到重置之间画红色虚线。试过 6px 实心条，太重、抢主环的视线；「每天一格」和「纯文字」两个方案也比较过。
- **客户端表格的宽窗口留白**：名字列封顶 260pt，紧跟「上次在线」列，状态 / 名字 / 上次在线成为左侧一组、用量数字在右侧一组。曾经名字列吸收全部多余宽度，宽窗口下名字和它的用量隔了一千多点。
- **不追求填满留白**。`DESIGN.md` 把留白、克制、避免信息过密列为设计价值；「更紧凑 / 更满」是需要论证的改动，不是默认的改进。曾有一轮把留白当缺陷去填，结果整体观感变差、全部回退。

## 改 UI 的流程

1. **先量再改**。尺寸用像素扫描量，不要目测——目测会被元素内部的文字边缘带偏。
2. **改完必须看实机截图**。有改动只看代码就宣布完成，实际没生效（例如在卡片外层加 frame 撑不出背景）。截图方法见 README（`BANDWAGON_SNAPSHOT_DIR`），不需要屏幕录制权限。
3. **审美取舍先问**，不替使用者决定。

### 像素扫描量边界

读截图像素、按亮度跳变找边界：

```swift
let rep = NSBitmapImageRep(data: NSImage(contentsOfFile: path)!.tiffRepresentation!)!
// 逐像素取 r/g/b，lum = 0.2126*r + 0.7152*g + 0.0722*b
// abs(lum - prev) > 0.015 记为一条边界
```

**扫描行要选在只有背景的位置**（卡片的内边距处），否则卡内文字边缘会被当成卡片边界。量宽度用卡片顶部内边距那一行，量高度用左右内边距那一列。

## 工程约定

- **工程自包含**，不引用仓库外任何东西（凭据辅助程序的安装位置除外）。
- **凭据只走辅助程序**。主程序不直接碰钥匙串；`ReleaseAssets/` 里的辅助程序是冻结件，摘要被三处锁定（见 `STRUCTURE.md`）。
- **3X-UI 写操作不在真实面板上试**，除非使用者明确同意；用 `Tests/http_fixture.py` 的 v3 夹具。面板升级后先对照上游源码重新核对接口（见 `STRUCTURE.md`「3X-UI 写操作」）。
- 提交信息用英文，正文说明「为什么」而不只是「改了什么」。
- **必须用 macOS 26 SDK 的产物标记构建**。`Package.swift` 给主目标加了
  `-Xlinker -platform_version -Xlinker macos -Xlinker 15.0 -Xlinker 27.0`：
  不加的话 SwiftPM 链接出来的产物把 `LC_BUILD_VERSION.sdk` 记成 15.0，而编译实际用的是
  27.0 SDK，系统据此按**旧设计语言**绘制窗口按钮、窗口圆角、侧栏开关等系统控件——表现为
  红绿灯是扁平实色、没有渐变高光，窗口圆角偏小。加了之后记录为 `minos 15.0 / sdk 27.0`，
  既拿到新外观又保留 macOS 15 兼容。**升级 Xcode 大版本后要同步改这里的 `27.0`。**

## 踩过的坑

- **重新打包后要 `pkill -9 -x Bandwagon` 并等两三秒再 `open`**。普通 `pkill` 加短等待时旧进程可能还在，而打包脚本已经换掉了 `.app`，`open` 会复用旧进程：应用在跑、主线程空闲，但**没有任何窗口**。看起来像布局死循环，其实是打包流程问题。
- **窗口被其他应用完全遮住时，`screencapture -l` 会返回空白帧**，而辅助功能树内容完整，容易误判成「页面渲染空白」。
- **把窗口高度设到接近屏幕高度会让窗口进入原生全屏**，之后通过辅助功能设置尺寸和位置全部「返回成功但被忽略」。需要检查并清除 `AXFullScreen`。
- **裸 `swiftc` 编译含 `@Observable` 的文件会报 `ObservationMacros ... malformed response`**：外部宏需要 `-plugin-path`，SwiftPM 会自动注入、裸调不会。`scripts/test.sh` 已处理。
- **`grep "\.env"` 会误报** `ProcessInfo.processInfo.environment` 和 SwiftUI 的 `.environment(model)`，要看具体命中行。
- **`open --env` 不会把环境变量传给应用**（macOS 26 实测：应用正常启动，但 `DevSnapshot.directory` 仍为 nil，一张图都不出）。`DevSnapshot` 的正确用法是先用环境变量直接启动二进制，再 `open` 一次把窗口激活——它靠 `cacheDisplay` 截图，必须有可见窗口，后台启动时 `isVisible` 为假，只会产出 `menubar.png`（那张走 `ImageRenderer`，不需要窗口）。完整命令见 `Sources/Bandwagon/Views/Shell/DevSnapshot.swift` 的文档注释。
